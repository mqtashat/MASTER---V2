## 1. بنية بسيطة قابلة للنمو

واجهة عربية واحدة، وخادم تطبيق واحد منظم إلى وحدات داخلية، وعامل خلفي للمهام الثقيلة، وSupabase/PostgreSQL قاعدة مركزية مع تخزين خاص للملفات. يشارك الخادم والعامل عقود الأنواع ومنطق الحساب، ولا يعيد المتصفح تطبيق المحاسبة أو العمولات.

خدمات داخل التطبيق: استيراد، تعريفات، مستندات، ذمم وتخصيص، مبيعات وكميات، تقويم وأهداف وعمولات، جغرافيا، وتقارير. هذا فصل مسؤوليات داخل مشروع واحد، لا اقتراح شبكة خدمات مصغرة تزيد التعقيد التشغيلي.

المتصفح يستقبل صفحة نتائج وإجماليات جاهزة، ثم يجلب التفاصيل عند الطلب. لا يحمل مئات آلاف الصفوف ليجري عليها filter/reduce، ولا يُنشئ نافذة خريطة لكل نقطة مخفية.

## 3. الاستيراد الكبير دون فقد أو مضاعفة

1. رفع الملف مرة واحدة إلى تخزين خاص، وإنشاء دفعة ونوع حركة واختيار ورقة.
2. العامل يقرأ XLS/XLSX في بيئة مناسبة للذاكرة والـCPU؛ قراءة متدرجة حيث يدعم التنسيق، أو تحويل داخلي مؤقت ثم دفعات. لا وعد بأن كل ملف XLS قديم قابل للبث دون ذاكرة. حدود حجم معلنة ورسالة واضحة وتقسيم ملف عند الحاجة.
3. إدخال أولي إلى staging عبر دفعات محدودة أو COPY عبر اتصال موثوق، لا آلاف طلبات شبكة منفردة، ولا COPY بصلاحيات واسعة في المتصفح. [S1]
4. فحص كامل للمراجع والتواريخ والمبالغ ومجموعات السند، ثم معاينة مجمعة مع أمثلة وروابط جميع الأخطاء. لا تعتمد العينة بدل الفحص الكامل.
5. حساب fingerprint للسند من الرأس وقائمة التفاصيل مع عدد مرات كل صف متماثل. لا استخدام Set أو DISTINCT على أجزاء التحصيل. تنسيق العرض/ترتيب الصفوف لا ينشئ تغييرًا تجاريًا إذا كانت التفاصيل نفسها.
6. بعد اعتماد المستخدم، قفل منطقي قصير أو ضبط نسخة للسند/العائلة المتأثرة؛ مقارنة إصدار المصدر المرجعي الذي بنيت عليه المعاينة، ثم كتابة مستند/أثر مالي/حدث تحديث في معاملات مضبوطة.
7. checkpoints بالوحدات المكتملة ومعرفات أثر فريدة. عند إعادة المحاولة تكتشف الوحدات المكتملة بدل إضافتها من جديد. تضمين `job_type` وbatch_id ومنع عامل آخر من الالتقاط بلا lease.
8. تحديث الذمم وFIFO تدريجيًا للنطاق المتأثر فقط وفق PERF-002 والتحقق، ثم نشر النتيجة المتسقة للمستخدم. لا تبدأ إعادة حساب لكل التاريخ عند اكتمال كل ملف؛ المطابق والمعلّق لا يغيران النتائج المالية. سجلات staging ليست مرئية كحركات معتمدة.

**الذرية:** نقترح اعتماد كل سند كامل مع أثره المالي الضروري ذريًا، والدفعة لها إجمالي تقدم ومخرجات معلنة. اعتمد المستخدم في DATA-005 قبول السندات الصحيحة وتعليق السندات ذات الأخطاء كاملة؛ تظهر أعداد المعتمد والمعلّق والمستبعد دون إعلان نجاح كامل للدفعة. اعتماد السند بعد تصحيحه يعيد فحصه ويطبق حماية التعديلات اليدوية، ولا يكرر السندات التي اعتمدت سابقًا. لتقارير تعتمد نتائج مشتقة نستخدم جيل نشر/نسخة قراءة؛ لا نخلط Ledger جديدًا بملخص قديم بصمت. يمكن إبقاء آخر نتيجة منشورة مع عبارة «قيد التحديث» إلى اكتمال التحقق. لا نحتاج معاملة واحدة طويلة تحبس قاعدة البيانات لمليون صف.

**تسابق التحديثات:** للمهام scope/version وlease ومقارنة إصدار عند النشر؛ نتيجة مهمة قديمة لا تستبدل نتيجة أحدث. إخفاق التحديث مشتقًا لا يلغي أصلًا صحيحًا بلا إجراء معروف. التصنيف الجغرافي يمكن أن يتأخر مع علامة حالته دون تعطيل مبيعات سليمة.

**فشل/استئناف:** retry محدود مع backoff للأخطاء المؤقتة، وأخطاء البيانات لا تعاد آليًا بلا تعديل. إن مات العامل بعد الحفظ وقبل إقرار الرسالة، المعرفات الفريدة والمعاملة تمنع تكرار الأثر. ضمان تسليم الطابور وحده لا يضمن أثرًا ماليًا مرة واحدة. [S2]

**تشغيل العامل:** الرفع الكبير وExcel والتصدير وإعادة الحساب الثقيلة لا توضع في طلب Edge Function واحد طويل. حدود الذاكرة والمدة وCPU موثقة وتتغير حسب المنصة، لذلك يقاس العمل ويجزأ أو يشغل بعامل مناسب. [S3] استخدام waitUntil لا يلغي هذه الحدود.

**الحذف والتراجع:** السلوك معتمد في DATA-007 وTXN-004. حذف الدفعة يتراجع عن أثرها: يزيل الجديد غير المعدل لاحقًا، ويستعيد السابق عند تحديثه بهذه الدفعة دون تغيير لاحق، ويبقي المطابق، ويعرض التعديل اللاحق للمراجعة دون حذف أو استعادة تلقائيين. الحذف الفردي يزيل السند وتفاصيله من البيانات الفعالة دون استعادة نسخة أقدم تلقائيًا. المعاينة قبل التأكيد وتحديث النتائج المرتبطة وحفظ الأصل والسجل معتمدة. مقارنة إصدارات السند قبل الدفعة وبعدها وحالته عند التنفيذ وسيلة تنفيذ مقترحة لضمان هذه القواعد؛ لا يكفي حذف كل ما يطابق مفاتيح الملف. تفاصيل الصلاحيات والإقفال وخيارات حسم التعارض والاستعادة المستقلة وإعادة الرفع تبقى في OPEN-028.

### 3.1 عقد المصدر المحدث وفحوصه المقترحة

مصدر المتطلبات INV-009 وRET-006 وتوضيح المستخدم بتاريخ 01/10/2026، مع نتيجة فحص المصدرين المصححين INV-010 وRET-007. أُنجز الفحص والمقارنة للقراءة فقط؛ البنود التالية متطلبات تنفيذ وفحوص قبول لاحقة وليست نتائج اختبار تطبيق. أُغلقت ملاحظة أصفار كمية العروض في النسختين الجديدتين، وتبقى حالة المصدر السابق مفيدة لاختبار اكتشاف التعارض دون تغيير الخام.

- ربط الأعمدة بأسمائها، لا بمواقعها: نسخة الفواتير 16 عمودًا والمرتجعات 15. أضيفت Longitude وLatitude وQuantity للمصدرين، وDocumentTypeID للفواتير فقط. لا يطلب عمود Location من النسخة الجديدة. تتبع نسخة عقد المصدر حتى لا يجعل غياب الأعمدة في الملف القديم قيمة صفرية أو يمحو بيانات النسخة الأغنى دون معالجة إعادة الرفع المتفق عليها.
- كل خلايا البيانات نصوص في الملفين. قراءة DocumentDate بصيغة DD/MM/YYYY، والمبالغ والكميات كقيم عشرية تحفظ دقة المصدر، والإحداثيات حسب أسمائها؛ تبقى معرفات العملاء والموظفين والأصناف والسندات نصوصًا. لا إسقاط لكسور الباكيت من المصدر الخام أو افتراض أن خانة نصية ليست رقمًا صالحًا؛ توجيه NUM-001 للأعداد الصحيحة وموضعه الحسابي OPEN-042 منفصلان عن قراءة الأصل.
- DocumentTypeID نص تصنيف نقدي/ذمم؛ العينة تحمل «فاتورة نقدي» و«فاتورة ذمم». لا تحويله إلى عدد بسبب اسمه، ولا إدخاله في مفتاح السند أو تحديد نوع الحركة منه. لا افتراض تصنيف عند غياب الحقل أو ظهور قيمة غير معروفة؛ سياسة معالجة القيمة غير المدعومة تراجع قبل التنفيذ.
- Quantity كمية الصنف للمباشر والعروض دون Bonus وفق توضيح المستخدم. يحفظ الخام كما ورد، بما فيه الصفر والكسور. تُعرض ملاحظة التحقق عند قيمة عروض موجبة وكمية صفر للمراجعة؛ لا تصحيح تخميني ولا استبدال بالمؤشر المكافئ، ولا جمع كمية مباشرة فعلية مع كمية عروض مكافئة تحت إجمالي فعلي واحد. لا يغيّر الحقل الجديد المبالغ المالية أو QTY-002.
- فحص الاتساق داخل السند يشمل DocumentTypeID حيث يوجد وإحداثيات الرأس، إلى جانب بيانات العميل والموظف. نوع الحركة ما زال اختيار المستخدم بأحد الأزرار الثلاثة؛ تصنيف المرتجع يبقى RET-005. تفاصيل بوابة الاعتماد لأصفار العروض أو إحداثيات ناقصة/متعارضة ليست قرارًا جديدًا معتمدًا بمجرد الفحص.
- Longitude للطول ضمن −180 إلى 180، وLatitude للعرض ضمن −90 إلى 90. فحص وجود الزوج واتساقه لا يثبت دقته ميدانيًا؛ لا عكس تخميني للقيم ولا تعويضها بموقع العميل، ولا اختراع وقت إصدار من اسم الملف.

## 4. القراءة والبحث والجداول

- pagination في الخادم: مقترح 50 صفًا افتراضيًا و100 اختياريًا. الانتقال العميق يستخدم cursor يحتوي كل أعمدة الترتيب مع معرف فريد، لا OFFSET متزايدًا إلى آخر التاريخ. أي قفز لصفحة رقمية كبيرة له تصميم مستقل لا ادعاء أنه cursor مجاني. [S4]
- العقد يعيد العناصر، cursor التالي، الفلاتر الفعلية، إصدار البيانات، تاريخ الاحتساب، ومؤشرات الاكتمال. عمود cursor ضمن SELECT، مع اختبار أنه يتقدم وينهي القراءة. ترتيب حتمي عند تعادل التواريخ.
- البحث عن رقم العميل/السند يحفظ الأصفار ويعالج الأرقام العربية بما لا يغير الهوية؛ اسم العميل له مفتاح بحث مطبع منفصل عن الاسم الأصلي. اختيار فهرس نصي/ثلاثيات حروف بعد قياس أسماء عربية حقيقية؛ لا تغيير هجاء أسماء العرض.
- طلب مجمع للأسماء والمجاميع المطلوبة، لا استعلام لكل عميل أو صف. الأعمدة الكبيرة والتفاصيل JSON تحمل عند فتح السند.
- الإجماليات من استعلام مجمع كامل النطاق لا من الصف الحالي أو أول حد API. الإجماليات الدقيقة الثقيلة يمكن أن تأتي كجزء مستقل بنفس نسخة النتيجة؛ لا عدد تقريبي بدون تسمية.
- لا fetch لجميع السجلات ثم إخفاء الزائد بالجداول الافتراضية. virtualization يحسن رسم النتائج المحملة فقط، ويعمل مع pagination ولا يستبدله.

## 5. تجميعات صحيحة وسريعة

تجميعات يومية للمبالغ على الأبعاد المطلوبة، ثم نتائج أداء للفترة حسب قواعدها. لا نحول كل تغيير فلتر إلى إعادة قراءة كل التاريخ.

- عند جمع فواتير مع تفاصيل وأجزاء تحصيل وتخصيصات، تجمع كل علاقة متعددة أولًا بالمستوى المطلوب؛ يمنع ضرب الصفوف بسبب joins عديدة ثم تضخيم المبلغ.
- مبالغ يومية قابلة للجمع، لكن عدد العملاء المميزين ليس مجموع أعدادهم اليومية. أهلية العميل تحسب على صافي فترته، والفاتورة تعد من الرؤوس، لا من سطور الأصناف.
- snapshots للفترات المقفلة؛ نتائج حية لها إصدار مدخلات وقواعد وتقويم ومشرفين. البطاقة والكشف يقرآن نفس run أو نفس سياق محرك الحساب.
- تجميع العمولة لا يسبق تطبيق السياسة المطلوبة: لكل صنف/شريحة ومعدل في حالة الأصناف، ولكل عميل أو فاتورة عند شروط التأهيل. لا تجميع يفقد البعد اللازم ثم محاولة استعادته.
- الرصيد الحالي مشتق سريع من Ledger. الرصيد التاريخي يحتاج حركات حتى التاريخ أو نقطة بداية محفوظة متوافقة مع إصدارها، لا استخدام رصيد اليوم لكل تاريخ.
- المحاسبة/التصنيف المرتبط برصيد سابق يعاد حسابه من أقدم تاريخ تأثر حتى نهاية النطاق المتأثر، لا فقط يوم السند الجديد.

| --- | --- |
| سند أو إلغاء/تصحيح مالي | العميل/العائلة من أقدم تاريخ متأثر، وموظف/صنف/فترة أداء ذات صلة |
| تحصيل الرئيسي | العائلة وتخصيصاتها اللاحقة؛ لا ذمم جميع العملاء |

الفترات المغلقة لا يعاد نشرها صامتًا. الأرصدة/نتائج الأداء والجغرافيا المختلفة تعرض حداثتها، والمقارنة المباشرة تستخدم نقطة بيانات متوافقة.

### التحديث التدريجي للذمم وFIFO — PERF-002

**المعتمد:** رفع ملف لا يعيد تشغيل حسابات كل العملاء أو الأشهر. يستخدم الجديد الحالة الصحيحة المحفوظة، والمطابق لا يشغّل عملًا ماليًا. التصحيح التاريخي يتتبع أثره في نطاقه فقط، دون التضحية بصحة الرصيد أو إسقاط الديون القديمة المفتوحة. الآلية التالية مقترحة لتحقيق هذا الشرط، وليست مخطط قاعدة بيانات معتمدًا.

**حالة مالية قابلة للاستكمال:** حفظ الرصيد الرسمي، والمتبقي من كل افتتاحي وفاتورة مؤهلة، والتخصيصات ومصادرها، وأي مبالغ غير مخصصة وفق السياسة التي ستعتمد. رصيد العميل الإجمالي وحده لا يكفي لاستكمال FIFO. ترتبط الحالة بإصدار المدخلات والقواعد وآخر موضع مكتمل في ترتيب FIN-001، ويمكن إنشاء نقاط استئناف دورية؛ نقطة الاستئناف لا تستبدل Ledger ولا تعد رصيدًا افتتاحيًا سنويًا جديدًا.

| نوع التغيير | العمل المطلوب وحدوده |
| --- | --- |
| سند مطابق بعد المقارنة | حفظ نتيجة الرفع/التدقيق اللازمة فقط؛ لا قيود أو تخصيصات أو مهمة ذمم جديدة |
| سند جديد لاحق لآخر موضع مكتمل | تطبيق أثره مرة واحدة على الحالة الصحيحة، وقراءة الديون المفتوحة المؤهلة اللازمة للتخصيص؛ لا مسح جميع الفواتير المسددة أو ملفات المصدر القديمة |
| سند قديم أو تعديل أو حذف أو تراجع عن دفعة | تحديد أصغر موضع متأثر بين النسخة السابقة والجديدة، والبدء من أحدث نقطة صحيحة قبله، ثم معالجة الحركات التابعة في نطاقها |
| تغيير العميل أو العائلة ذات الصلة | شمول النطاق القديم والجديد والتبعيات بين الفروع والرئيسي وفق السياسات المعتمدة؛ لا الاكتفاء بالعميل الجديد |
| تغيير رقم/تاريخ سند دون تغيير مبلغه | فحص تغير موضع FIN-001؛ نفس الرصيد النهائي لا يثبت سلامة التخصيص أو تصنيف المرتجعات اللاحقة |
| تغيير المندوب وحده | تحديث إسناد الذمم والبطاقات والنتائج للموظفين المتأثرين؛ لا إعادة FIFO إذا لم تتغير مدخلاته |
| تغيير موقع/وصف فقط | تحديث النتائج ذات الصلة دون احتساب مالي |
| تصحيح افتتاحي | الاستئناف قبل أثره بتاريخ 1/1 للحساب/العائلة المتأثرة؛ انتقال الأثر بين السنوات يخضع لـOPEN-032 |

**تحديد الترتيب والنطاق:** «جديد في الملف» لا يعني «لاحق في الحساب». يقارن الموضع الكامل بتاريخ السند وأولوية نوعه ورقمه والترتيب الحتمي المكمل، دون وقت إصدار مختلق. في العائلة التي تتشارك التخصيص أو تصنيف مرتجع الرئيسي، تشمل نقطة الاستئناف نطاق الاعتماد اللازم؛ لا تجمع حالات فروع من إصدارات غير متوافقة. يلزم كشف التبعيات حتى لو لم يتغير إجمالي دين العائلة.

**التصحيح الرجعي:** تبطل الحالة والنقاط اللاحقة التي تتأثر، مع الاحتفاظ بالسابق الصحيح والسجل. يعاد الحساب من أقرب نقطة صحيحة قبل التغيير حتى نهاية الأثر؛ عند عدم وجود نقطة صالحة يبدأ من الأساس الصحيح لهذا النطاق فقط، دون اختراع حالة افتتاحية. يمكن إيقاف الامتداد مبكرًا فقط عند إثبات تطابق الحالة الكاملة المؤثرة في المستقبل واستقرار المدخلات اللاحقة، وليس لمجرد تساوي الرصيد النهائي أو انتهاء شهر. لا يشترط تنفيذ هذا التحسين الإضافي قبل ضمان صحة النتائج.

**التبعيات المالية:** قد يغيّر التصحيح الرصيد السابق لمرتجع ومن ثم تصنيفه وفق RET-005 أو تخصيص تحصيل لاحق. تتبع هذه التبعيات في النطاق نفسه، مع تطبيق دورة التصحيح التي ستحسم ضمن OPEN-022/029/032. لا تعدل تصنيفات أو تسويات غير معتمدة تحت اسم تحسين الأداء. تبقى نسخ العمولات المقفلة محفوظة وفق PERIOD-001/002.

**المهام والنشر:** تجمع تغييرات الدفعة أو دفعة المعالجة في مهمة للنطاق المتأثر من أقدم موضع، بدل إعادة السلسلة كاملة لكل صف. يطبق ترتيب FIN-001 داخل المعالجة، مع الاحتفاظ بوحدة اعتماد السند الكامل وحالات DATA-005. تضبط المهام المتزامنة على النطاقات المتداخلة بإصدارات أو تسلسل مناسب، وتستأنف عند الانقطاع دون مضاعفة الأثر؛ مهمة قديمة لا تنشر فوق إصدار أحدث. تعرض الشاشة نتيجة متسقة منشورة وحالة «قيد التحديث» عند الحاجة، ولا تخلط رصيدًا جديدًا بتخصيص قديم باعتباره مكتملًا. فتح الصفحة لا يشغّل FIFO.

**حد العمل الكامل:** التهيئة الأولى، أو استعادة حالة مشتقة مفقودة، أو تغيير قاعدة مالية واسعة الأثر قد تحتاج بناءً أوسع بنطاق وسبب واضحين. هذا مسار صيانة مستقل مقترح، وليس خطوة تلقائية مرتبطة بكل رفع. المقياس هو مقدار البيانات المتأثرة والديون المفتوحة المطلوبة، لا إعادة قراءة كل ما تراكم من ملفات.

### احتساب التحصيل والتخصيص — متطلبات معتمدة

COL-007 يحتسب الشيك المؤجل والمستحق تحصيلًا بتاريخ سند التحصيل دون متابعة صرف أو تأكيد بنكي؛ لا توجد مهمة انتظار أو تحقق صرف في نطاق هذه المتطلبات. FIN-004 يخصص التحصيل للمتبقي المدين من الافتتاحي أولًا؛ بعد نفاده يخصص باقي السند للفواتير المفتوحة بالأقدم أولًا عبر الفروع المؤهلة وفق COL-008، مع السداد الجزئي وعدم تجاوز المتبقي على كل دين.

تحفظ collection_parts الأصلية بتعددها، بينما allocations تمثل تخصيص النظام على الافتتاحي ثم الفواتير؛ مجموع الأجزاء يحسب مرة واحدة ومجموع التخصيص لا يضاف إليه كتحصيل آخر. قراءة كشف العائلة والفرع يجب أن تستخدم المصدر والتخصيص في مستوييهما الصحيحين. أولوية أرقام الفواتير عند تساوي التاريخ معتمدة في FIN-001؛ نطاق سند الفرع وفواتير الرئيسي والزائد يبقى في OPEN-029؛ الافتتاحيات السنوية معتمدة FIN-002/003، وأولوية تسديد متبقيها المدين FIN-004؛ تفاصيل الربط والمفاضلة بين افتتاحيات متعددة ومطابقتها في OPEN-032.

PERF-002 يجعل التحديث تدريجيًا للنطاق المتأثر، مع تصحيح التخصيصات التابعة عند تغيير مبلغ/تاريخ/عميل التحصيل أو حذفه وعند تغير الفواتير ذات الصلة؛ لا إعادة حساب لكل التاريخ عند كل رفع. الآلية المقترحة أعلاه تعيد التحقق عند الاعتماد وتمنع التخصيص المزدوج بالتزامن. صرف الشيك خارج النظام لا ينشئ حدث تحصيل ثانيًا. سياسة الإقفال تبقى ضمن قراراتها المفتوحة.

### تصنيف المرتجعات — معتمد RET-005

التصنيف وفق الرصيد الرسمي قبل أثر السند في تاريخه: الموجب يجعل السند كاملًا ذممًا ويخفض الرصيد بكامل القيمة ولو تجاوز الدين؛ الصفر أو الدائن يجعله نقديًا بلا أثر على الذمم. الرئيسي يفحص صافي العائلة، والفرع حسابه وحده دون دين شقيق، والمستقل حسابه وحده. المصدر غير المكتمل الذي لا يثبت رصيدًا سابقًا لا ينتج صفرًا مفترضًا؛ يظهر بحاجة للمراجعة.

سابق 20 ومرتجع 50: قيد مرتجع دائن بقيمة 50 مرة واحدة ورصيد −30، أي 30 لصالح العميل؛ لا قيد نقدي إضافي ولا قص للمبلغ إلى 20. التصنيف من المرجع الرسمي لا من Preset أو الفلاتر أو يوم فتح التقرير. أولوية الحركات المتعادلة معتمدة FIN-001؛ تاريخ السعر للكمية وأثر العمولة والتسوية وإعادة التصنيف والإقفال ما زالت بقواعدها المفتوحة.

### ترتيب الحركات والتصنيف المتتابع — معتمد FIN-001

نفس ترتيب FIN-001 لمحرك الرصيد وتصنيف المرتجع وكشف الحساب والطباعة والتصدير. كل مرتجع يستخدم الرصيد الرسمي السابق له بعد الحركات والمرتجعات السابقة في الترتيب؛ لا يصنف كل مرتجعات اليوم من رصيد افتتاحه نفسه. عند تعادل تاريخ فواتير مؤهلة للتسديد تستخدم أولوية رقم الفاتورة تصاعديًا دون تغيير نطاق التخصيص.

تفاصيل تنفيذ مقترحة: ترتيب طبيعي للأرقام، ثم رقم العميل ومعرف ثابت عند تساوي الرقم، ومقارنة معلنة للنصوص غير الرقمية. cursor والحساب التراكمي والتصدير يجب أن تستخدم مفاتيح المقارنة نفسها. تغيير ترتيب ملفات الرفع أو صفوفها لا يغير نتيجة البيانات المعتمدة نفسها. تغيير رقم أو تاريخ سند قد يؤثر في ترتيب المعالجة؛ دورة التسوية وإعادة التصنيف والإقفال مستقلة، والقراءة لا تكتب أثرًا ماليًا.

### كشف الحساب — متطلبات المستخدم STMT-001/008

Ledger مرجع المبالغ المؤثرة. صفحة الكشف للقراءة والتحليل والعرض والتصدير؛ لا ترحيل أو إعادة توزيع أو تحديث رصيد رسمي عند فتحها أو فلترتها أو تخصيصها أو طباعتها. حفظ Preset يقتصر على إعدادات العرض وقائمة الإخفاء. تعديل السند يبقى في صفحته الأصلية.

التاريخ فقط، والوقت ملغى من الشاشة والمعاينة والمخرجات. FIN-001 يعتمد التاريخ تصاعديًا ثم أولوية الإشعارات المدينة، الدائنة، الفواتير، التحصيلات، المرتجعات؛ داخل النوع أرقام السندات تصاعديًا. تفاصيل المقارنة المكملة توثق بصورة حتمية مع حفظ معرفات المصدر. أرقام العملاء تطابق كاملة في البحث الرقمي مع حفظ الأصفار. «العائلة كاملة» من فرع ترجع لرئيسيه دون تكرار.

المخصص يعيد حساب السابق والمدين والدائن والنهائي دون تغيير الرسمي؛ المخفي داخل الفترة لا يغير السابق، والمخفي قبلها يستبعد أثره من السابق المخصص. أصل الرصيد من بيانات معلومة لا من صفر عند نقص الافتتاحيات. غير المؤثر والملغى يظهران للمراجعة دون إعادة أثر مالي.

**تصميم مقترح:** حساب النطاق والافتتاحي والأرصدة المتحركة في الخادم، ونشر نتائج العرض من نسخة متسقة، مع فصل مجاميع نتائج البحث عن الرصيد الرسمي. حسم أثر فلاتر المخصص في OPEN-030، وهوية الإخفاء بعد تعديل السند أو إعادة بناء Ledger وسلوك Preset عند تغير البيانات في OPEN-031. لا تعتمد قائمة الإخفاء على رقم السند وحده أو موضعه في الصفحة.

### الأرصدة الافتتاحية السنوية — معتمد FIN-002/003/004 وتفاصيل تنفيذ مقترحة

**المتطلب:** افتتاح 1/1 لكل سنة، قالب Excel بدءًا من 2027 وإضافة أو تعديل رصيد العميل في أي وقت. افتتاح سنة البدء 2026 صفر معتمد صراحة دون ملف، مع استمرار الإضافة والتعديل لاحقًا؛ تفاصيل الافتتاحيات في OPEN-032.

**استيراد معتمد FIN-003:** قسم الافتتاحيات داخل الحسابات ومدخل من ملف العميل، والسنة من الواجهة. القالب أربعة أعمدة: رقم العميل، الاسم، مدين عليه، دائن له. التحميل يعيد افتتاحيات السنة المسجلة ويترك غير المحدد فارغًا. المطابقة بالعميل والسنة؛ الجديد يضاف والمطابق يبقى والمختلف يعاين قبل الاستبدال؛ الغائب وفارغ الخانتين يبقيان دون تغيير، والصفر الصريح يسمح بالتصفير.

التكرار والسالب والجهتان الموجبتان والعميل غير المعروف أخطاء تحتاج تصحيحًا دون تغيير القيمة المحفوظة. تعارض الملف مع اليدوي يحافظ على اليدوي حتى اختيار قيمة الملف صراحة. السابق والجديد وسجل التغيير متطلبات معتمدة للإضافة والتعديل الفردي أيضًا. لا تعمم قواعد حذف دفعات الحركات على دفعات الافتتاحيات دون قرار.

**تصميم مقترح:** أساس مالي واحد فعال لكل عميل وسنة، مع نسخ وسجل للتعديلات. يفصل تاريخ أثر الافتتاحي 1/1 عن تاريخ الإجراء، ويطبق التصحيح بدل القيمة السابقة دون جمع النسخ. لا تضاف افتتاحية سنة فوق رصيد السنة السابقة الذي تمثله؛ يحسم تمثيل الانتقال والمطابقة والفروق والكشوف العابرة للسنوات قبل اعتماد مخطط التنفيذ. تحفظ مستندات السنوات السابقة دون تكرارها أو حذفها لهذا السبب.

تصحيح الافتتاحي قد يؤثر في أرصدة رسمية وتصنيف مرتجعات وتخصيصات تحصيل وفق قواعدها. المقترح معاينة الآثار وإعادة احتساب النطاق المتأثر ونشر النتائج من نسخة متسقة، مع سجل واضح للقديم والجديد. نطاق التأثير قد يمتد إلى عائلة العميل بسبب RET-005 وCOL-008؛ لا يفترض اقتصاره على صف العميل المصحح. تحديث سنة لاحقة ذات افتتاحي مدخل مستقل ومسار تعديل سنوات سابقة من تفاصيل OPEN-032، ولا يعتمد منع التعديل لاحقًا كحل.

تفاصيل الفواتير القديمة تفصل الرصيد ولا تنشئ دينًا إضافيًا؛ الافتتاحي الإجمالي غير المفصل لا ينتج تاريخ فاتورة أو مندوبًا مختلقًا. أولوية تسديد متبقيه المدين قبل الفواتير معتمدة FIN-004؛ ترتيب افتتاحيات حسابات متعددة مؤهلة وتسوية الدائن وربط التفاصيل والأعمار والمندوب تبقى للمراجعة. حقول الملف والمطابقة وقواعد إعادة الرفع وحماية اليدوي معتمدة FIN-003؛ تفاصيل التحقق من السنة وقراءة الخلايا والصلاحيات وحذف الدفعات وتحديث النتائج التاريخية تبقى للمراجعة.

**أولوية تخصيص معتمدة FIN-004:** يستخدم التحصيل المتاح لتسديد المتبقي المدين من الافتتاحي فقط، ثم الفواتير بالأقدم. لا يعدل أصل الافتتاحي، ولا يقتطع الأصل من كل تحصيل من جديد، ولا يحتسب السداد أثرًا ماليًا فوق قيد التحصيل. الافتتاحي الصفري أو المسدد لا يستهلك تخصيصًا، والدائن لا يعامل كدين موجب؛ تسويته التفصيلية مفتوحة.

مثال قبول حسابي: افتتاحي 500 وفاتورة 300 وتحصيل 600 ينتج تخصيصًا 500 للافتتاحي و100 للفاتورة، ويبقى 200 عليها. التحصيلان المتتاليان 200 ثم 400 يحققان التخصيص النهائي نفسه. إذا احتفظت فواتير قديمة يمثلها الافتتاحي، لا تدخل كمديونية ثانية عند تخصيص الباقي للفواتير؛ الربط التفصيلي والمطابقة قبل التنفيذ ضمن OPEN-032.

## 6. خرائط بحجم كبير

استخدام PostGIS للفحص المكاني والفهارس والاستعلام ضمن حدود العرض. الجداول تخزن هندسة العميل وهندسة موقع الفاتورة منفصلتين؛ ترتيب GeoJSON longitude ثم latitude مع اختبار واضح. المسافات بالأمتار عبر نوع/تحويل مناسب، لا درجات تعامل كأمتار. [S6]

الخريطة تحمل نقاط/عناقيد المنطقة المرئية، لا مئات آلاف العلامات. عند التصغير يستخدم الخادم تجميعًا مكانيًا/مربعات؛ عند التكبير تفاصيل أكثر وحد أعلى معلن. تُطلب البيانات بعد انتهاء الحركة أو زر «ابحث هنا» مع debounce وإلغاء القديم. Popup ينشأ عند الطلب.

تجميع المواقع القريبة بفهرس مكاني وبحث محيط محدود، لا مقارنة كل نقطة بكل النقاط O(n²). هندسة مضلع صالحة، وسياسة واضحة للنقطة الواقعة على الحد والتداخل وهامش GPS بعد اعتمادها. لا تستعمل bounds تقريبية للأردن دليلاً وحيدًا لعكس إحداثيات محتملة المعنيين.

طبقات الخريطة داخل حاوية مرنة، ResizeObserver، CSS ضمن الحزمة، ونوافذ معزولة بالترتيب البصري واختبار تكبير 200%. فشل خريطة لا يسقط بقية الصفحة.

## 7. الكاش والطباعة والتصدير

مفتاح الكاش يشمل المستخدم/نطاق صلاحياته، الفلاتر، محور التاريخ والقطع، وإصدار البيانات والقواعد. الاستيراد أو التصحيح يبطل ما تأثر أو يولد إصدارًا جديدًا؛ TTL وحده لا يكفي لماليات حديثة. لا تعطيل شامل للكاش ولا مشاركة كاش يسرّب نطاق فريق آخر.

لكشف الحساب، يشمل مفتاح النتيجة المقترح أيضًا العميل والنطاق والفترة والوضع الرسمي/المخصص وقاعدة الفلاتر وقائمة الإخفاء وإصدارها. لا تستخدم نتيجة الرسمي للمخصص أو نتيجة Preset آخر لمجرد تطابق العميل.

النسخة المقفلة غير متغيرة وقابلة للتخزين طويلًا. القراءة الحية تبين «حسب بيانات حتى...» و«آخر تحديث». إلغاء الطلب القديم يمنع استبدال النتيجة الأحدث بعد العودة المتأخرة.

**متطلب تصدير الحركات المعتمد INV-008/RET-004/COL-006:** في صفحة كل نوع خيار لتصدير الجدول المعروض وخيار لجميع سندات فترة مختارة، ضمن الصلاحيات. تاريخ الفترة DocumentDate للفواتير والمرتجعات و«التاريخ» للتحصيلات. التصدير الكامل لا يقتصر على الصفوف المحملة أو رقم الصفحة أو فلاتر صفحة باقية بصورة غير معلنة. الملخص بصف لكل سند، والتفاصيل بجميع بنود أو أجزاء السندات في النطاق؛ يحتفظ التصدير التفصيلي للتحصيلات بتعدد الأجزاء المتطابقة.

**متطلب كشف الحساب STMT-007/008:** كل PDF/Excel/Print يشمل جميع الحركات المطابقة للفلاتر، وليس الصفحة الحالية؛ المخصص يستبعد المخفي ويصدر أرقامه، والتاريخ فقط دون الوقت. المعاينة والمخرجات تثبت النطاق والفترة والفلاتر والوضع والإخفاء والترتيب وإصدار النتائج نفسه. لا تُتجاهل الفلاتر وفق اقتراح P07 القديم. هذا لا يغير خياري تصدير صفحات الحركات الثلاث أعلاه.

**تنفيذ مقترح:** التصدير الكبير مهمة خلفية مثبتة النطاق والإصدار والصلاحية؛ ترقيم متدرج للصفوف وملف خاص برابط محدود العمر. تصدير الفترة الكامل لا يعتمد على قائمة IDs الموجودة في المتصفح، ولا يعيد تشغيل حساب مختلف عن المعاينة لنطاقه. تصدير الصفحة الحالية يثبت سجلات تلك الصفحة وترتيبها، مع التحقق من الوصول عند إنشاء الملف. عند تغير الصلاحية قبل التنزيل يعاد فحص الوصول. PDF الطويل يقسم صفحات مع ترويسة ومجاميع سليمة، لا صورة عملاقة للجداول.

### 7.1 عرض الأداء والصور وكشوف العمولة

المتطلبات الجديدة CARD-001/002 وCOMM-001/003 وPERIOD-001/002 مثبتة من المحادثة المنقولة. تستخدم البطاقة والكشوف سياق حساب واحد للفترة والقطع وإصدار البيانات والقاعدة؛ طبقة قرارات الصرف تخص الكشف ولا تغير مؤشرات البطاقة.

حفظ الصورة ينتظر اكتمال عرض البطاقة وخطها وصورها، ثم يلتقط الأقسام الظاهرة وكامل ارتفاعها دون أدوات التحكم. لا طلب حساب مالي أو إغلاق ضمن الحفظ. طريقة إخراج الصورة وحدود الحجم تفاصيل تنفيذ تقاس على بطاقات طويلة.

الأقسام والأزرار والأعمدة الديناميكية تستمد مفاتيحها وتعريف عرضها من الأهداف المدعومة؛ لا تعتمد على مطابقة الاسم الظاهر وحده. تجمع الأعمدة القابلة للجمع فقط، ولا تضاعف مبيعات الفريق عند وجود المشرف ومندوبيه.

الإغلاق يحفظ النتيجة والمدخلات وإعدادات القواعد اللازمة لتفسيرها، وقراءة المغلق تستخدم النسخة المحفوظة. لا يغير استيراد متأخر تلك النسخة تلقائيًا. تنفيذ مسار تصحيح الإدارة والإصدارات والتسويات يتبع قرار OPEN-034؛ لا تختلق معادلة لتداخل التعديلات اليدوية قبل OPEN-033.

## 8. الصلاحيات وسلامة النتائج

اقتراح Supabase Auth وهوية موثقة، وصلاحيات مخزنة في مصدر لا يحرره المستخدم. RLS للكيانات المعرضة، وسياسات نطاق فريق/حساب صحيحة؛ grant الوصول إلى جدول ليس بديلًا عن RLS. Views/RPC والتصدير تخضع لنفس النطاق. لا secret/service_role في المتصفح. [S8]

العمليات ذات الامتياز تمر بخدمة واضحة تتحقق من الفاعل والنطاق؛ لا SECURITY DEFINER عشوائيًا لإخفاء خطأ صلاحية. الملفات الخام والتصدير في تخزين خاص. سياسة هوية المستخدم تختلف عن حالة الموظف الوظيفية.

نراجع التغييرات الحالية للمنصة قبل التنفيذ. فُتح سجل Supabase HTML بعد تعذر قراءة رابط Markdown بأداة الويب. من نقاط التنفيذ التي يلزم مراعاتها: الوصول إلى جداول Data API يحتاج تحققًا صريحًا من grants/settings، وإصدارات Node/TypeScript تُثبت بما تدعمه المكتبات وقت البناء؛ لا ننسخ بيئة مشروع قديم بلا مراجعة. [S9]

**صلاحيات معتمدة AUTH-001/003:** حساب الإدارة كامل الصلاحيات، والحسابات العادية بمصفوفة الصفحة والتبويب والإجراء، وغير الممنوح ممنوع. يطبق التحقق على الطلب نفسه والروابط والتصدير وحفظ الصورة، لا على إظهار الزر فقط. تعديل شهر مغلق وإغلاقه وإعادة فتحه للإدارة PERIOD-002. إيقاف المستخدم يحفظ تاريخ عملياته، وإعادة تعيين الدخول لا تكشف الرمز السابق؛ نطاق البيانات وأولوية القوالب والاستثناءات والجلسات في OPEN-035.

أمثلة الأدوار في المرفق لا تستبدل مصفوفة المستخدم بصلاحيات ثابتة. إجراء DELETE يستدعي سلوك DATA-007/TXN-004 القائم ويحفظ الأثر، ولا يغير نموذج حذف السند المالي من تلقاء نفسه.

## 9. أهداف أداء قابلة للقياس

مجموعة مرجعية مقترحة للاختبار: مليون سطر بيع، نحو 200 ألف رأس فاتورة، 100 ألف سطر مرتجع، 100 ألف جزء تحصيل، 20 ألف عميل، 100 موظف، وأسعار وتغييرات لعامين. نحافظ على توزيع واقعي: عملاء كثيفو الحركة، عائلة كبيرة، فواتير كثيرة الأصناف، أجزاء تحصيل متطابقة، بيانات ناقصة وتغييرات رجعية. هذه بيانات اختبار مقترحة وليست حجم ملفات محمد الحالي.

اختبار قراءة متزامنة أولي: 20 مستخدمًا مع مهمة رفع 100 ألف صف ومهمة تصدير، على بيئة اختبار معروفة الموارد والمنطقة وحجم الاتصال. نقيس الحالة الباردة والدافئة منفصلتين ثم نعدّل الموارد أو الأهداف بالنتائج.

### 9.1 صحة الأمثلة وفصلها عن التشغيل

متطلب المستخدم أن تكون الأمثلة صحيحة مع عدم اعتمادها بيانات فعلية. الفحوص التالية لتطبيق هذا المتطلب عند التطوير، وليست إعلانًا عن اختبارات تطبيق نُفذت.

| مثال لسلوك صحيح | أعمدة وقيم ووحدات ومراجع متسقة، وتجميع سندات وحسابات يطابقان القواعد المعتمدة والنتيجة المتوقعة |

| تغيير ترتيب السند أو تصحيح يؤثر في مرتجع لاحق | تطابق التصنيف والتخصيص والرصيد السابق لكل حركة مع المرجع بعد تطبيق سياسة التصحيح المعتمدة |
| حذف سند أو التراجع عن دفعة | تطبيق TXN-004/DATA-007 أولًا، ثم تحديث النطاق المتأثر فقط؛ المطابق والتعديلات اللاحقة المحمية لا تزال على حالها |
| تصحيح افتتاحي أو فقد نقطة استئناف | عدم استخدام نقطة متأثرة أو اختراع صفر؛ العودة إلى أساس صحيح في النطاق، وتطبيق قواعد السنوات عند حسم OPEN-032 |
| تغيير المندوب أو الموقع دون تغيير مدخلات المالية | تحديث الإسناد/العرض ذي الصلة، دون إعادة توزيع التحصيل |
| مهمتان متزامنتان أو توقف ثم استئناف | لا تخصيص مزدوج ولا فقد أثر ولا نشر نتيجة أقدم فوق الأحدث؛ النتيجة المعلنة متسقة |
| فتح كشف الحساب أو الذمم | قراءة النتيجة فقط؛ لا إنشاء مهمة FIFO بمجرد الفتح أو البحث أو التصدير |
| تصحيح مالي يمس فترة عمولة مقفلة | لا يستبدل نسخة العمولة المقفلة تلقائيًا؛ يتبع مسارها المستقل |

**قياس لاحق:** تسجيل زمن القراءة والمقارنة والحساب والنشر كلٌّ على حدة، وعدد السندات المتغيرة والحركات المعاد احتسابها والديون المفتوحة المقروءة والنطاق والتاريخ اللذين عولجا. تقارن دفعات صغيرة متماثلة مع تضخم التاريخ غير المتأثر للتأكد أن الرفع لا يتحول إلى مسح شامل؛ يقاس التغيير الرجعي منفصلًا عن الإضافة اللاحقة. لا تعلن أزمنة استجابة أو نجاح اختبارات حمل قبل تنفيذها.

### 10.5 قبول أثر استثناء الموظف — CAL-002، حالات مخططة

يحفظ نمط الأثر على سجل الاستثناء مع الموظف والفترة والتواريخ والسبب وإصدار التعديل؛ هذا وصف تنفيذ مقترح لدعم الاختيار المعتمد عند الإضافة. تقرأ الصفحات ومحرك الهدف الاختيار نفسه، مع سجل يحفظ السابق والجديد. لا تعمم سياسة خطة واحدة على جميع الاستثناءات.

| الحالة | النتيجة المطلوب التحقق منها |
| --- | --- |
| إضافة استثناء موظف | ظهور خيارَي هدف ثابت/هدف متناسب مع الأيام، وحفظ الاختيار مع الاستثناء |
| 25 يوم عمل وهدف 10,000 واستثناء واحد لـ3 أيام مؤهلة — ثابت | تصبح الأيام 22، ويبقى الهدف 10,000؛ يوضح أن الاستثناء لم يخفض القيمة |
| المثال نفسه — متناسب | تصبح الأيام 22 والهدف 8,800؛ تعرض القيمة الأصلية والأثر وسببه |
| فتح الاستثناء المحفوظ أو إضافة استثناء آخر | الاختيار المحفوظ لا يتغير بسبب إعداد خطة أو اختيار استثناء جديد |
| الأهداف والبطاقة والتقويم | نفس الاستثناء ونمط الأثر والإصدار؛ لا نتائج متناقضة بين الصفحات |
| اختيار المتناسب | لا تعديل آلي لنسب العمولة أو مبالغ المكافآت أو سائر شروطها؛ يعاد تقييم تحقق الأهداف التابعة فقط وفق قواعدها |
| استثناء في فترة مفتوحة | تحديث الموظف والفترات والتبعيات المتأثرة مع السجل والصلاحيات؛ لا تغيير للمستندات أو Ledger/FIFO |
| فترة عمولة مقفلة | يبقى مسار الإدارة والإصدار المعتمد وفق PERIOD-001/002؛ لا استبدال صامت للنسخة التاريخية |

استكملت الحالات المختلطة والتداخل واليوم غير المؤهل وصفر الأيام في CAL-003 وحالات القبول التالية. تبقى الخطط متعددة المكونات والتقريب وتفاصيل أهلية الفترة في OPEN-006/036. حُسم أثر حركات يوم الاستثناء في CAL-004 مع بقائه مستقلًا عن اختيار تخفيض الهدف؛ الإسناد للمتابعة اليومية حُسم في CAL-005. هذه متطلبات تحقق مستقبلية، وليست اختبارات منفذة.

### 10.6 قبول جمع الاستثناءات وتقييم الشريحة — CAL-003/GOAL-007، حالات مخططة

يحسب الهدف من أصله وأيام الأساس ثم مجموعة الأيام المؤهلة المختلفة وسياسة كل يوم بعد حسم التعارض. لا يخفض الناتج السابق مرة ثانية. تربط نتائج الأهداف والشريحة والعمولة بنفس نسخة الاستثناءات والمدخلات، وتقتصر إعادة النتائج على الموظفين والفترات والتبعيات المتأثرة؛ لا تغيير في Ledger/FIFO بسبب هذا التعديل.

| الحالة | النتيجة المطلوبة |
| --- | --- |
| هدف 10,000 وأيام أساس 25، يومان ثابتان وثلاثة متناسبة | أيام الموظف 20، والتخفيض 1,200، والهدف 8,800 |
| تغيير ترتيب إضافة الاستثناءات نفسها | النتيجة نفسها، دون تخفيض مركب أو اختلاف بحسب ترتيب الإدخال |
| استثناء متناسب لثلاثة أيام يضاف ثم يحذف | العودة إلى النتيجة من الأصل والاستثناءات الباقية، دون بقاء تخفيض محذوف؛ السجل محفوظ |
| تكرار يوم بالنمط نفسه | خصم يوم واحد فقط من الأيام، ومن التخفيض إن كان متناسبًا |
| يوم ثابت ويوم متناسب على التاريخ نفسه | تعارض يظهر لاختيار المعاملة؛ لا ترجيح صامت ولا أثر مزدوج |
| استثناء يصادف عطلة أصلية | لا خصم إضافي من أيام العمل أو قيمة الهدف |
| جميع الأيام مستثناة | المعدل اليومي غير قابل للاحتساب؛ لا قسمة على صفر ولا تحقيق أو شريحة تلقائية |
| هدف A معدل إلى 8,800 ومبيعات مؤهلة 9,000 | إنجاز يقارب 102.27% وتحقق شرط قيمة A، مع وجوب استيفاء بقية شروط الشريحة |
| هدف A ثابت 10,000 ومبيعات مؤهلة 9,000 | إنجاز 90%؛ لا يستخدم المقام 8,800 دون استثناء متناسب مؤثر |
| نسبة عمولة توضيحية 3% وكل 9,000 مؤهلة | عمولة 270؛ لا تستخدم 10,000 أو 8,800 أساسًا للعمولة لمجرد أنهما هدف |
| هدف مركب أو أصناف بنسب مختلفة أو قاعدة موظف مرتبطة | تبقى الشروط والقاعدة وأساس الأهلية والأولوية سارية؛ لا تعمم نسبة 3% أو تطبيق التناسب على مكونات غير مشمولة |
| البطاقة والكشف والفترة المغلقة | المصدر والإصدار نفسهما؛ الأصل والمعدل والأساس الفعلي واضحون؛ لا استبدال صامت لنسخة مقفلة |

حدود فترة أهلية الموظف حُسمت EMP-003؛ حُسم تقريب أهداف الأعداد الصحيحة GOAL-008؛ تبقى مكونات الخطة وصفر أيام الأساس وتفاصيل الفترات OPEN-006/008/036 وموضع التقريب العام OPEN-042؛ أثر الشهر الجزئي حُسم CAL-008. هذه الحالات لم تنفذ كاختبارات تطبيق أو حمل ضمن التوثيق.

### 10.7 قبول حركات اليوم المستثنى — CAL-004، حالات مخططة

| الحالة | النتيجة المطلوبة |
| --- | --- |
| مبيعات مؤهلة في يوم مستثنى بخيار ثابت | تدخل إنجاز الفترة والعمولة بشروطهما؛ يبقى اليوم مستثنى ولا تخفيض للهدف بسبب ذلك الاستثناء |
| مبيعات مؤهلة في يوم مستثنى بخيار متناسب | تدخل إنجاز الفترة والعمولة بشروطهما؛ يستمر استبعاد اليوم وتخفيض الهدف المعتمد |
| هدف صافي ومبيعات 500 ومرتجعات 100 مؤهلة | يضيف اليوم 400 إلى إنجاز الفترة؛ لا يتجاهل المرتجع لأن يومه مستثنى |
| هدف لا يستخدم صافي المبيعات | لا يفرض خصم المرتجعات عليه من المثال؛ يطبق تعريف المقياس نفسه |
| تحصيل في يوم مستثنى | يدخل هدف التحصيل إذا استوفى شروطه، دون اعتباره مبيعات أو تكرار أثره المالي |
| حركة لا تحقق شروط هدف أو قاعدة | تبقى حالة أهليتها وفق القاعدة؛ وجودها في يوم مستثنى لا يمنحها استحقاقًا تلقائيًا |
| إعداد الاستثناء أو تغييره | لا يحذف حركة أو يغير DocumentDate أو Ledger/FIFO أو تصنيف المرتجع المالي أو إسناد موظفه |
| البطاقة والكشف مع وجود حركات في يوم مستثنى | نفس بيانات الإنجاز المؤهلة ونسخة الهدف المعدل والقواعد؛ لا فلتر خفي يستبعد كل حركات أيام الاستثناء |
| فترة عمولة مقفلة | تتبع مسار PERIOD-001/002، دون استبدال النتيجة المحفوظة تلقائيًا |

اعتمد الإسناد اليومي في CAL-005 وحالاته التالية، ثم الافتراضي الميلادي CAL-006 وأيام العمل والعطل CAL-007؛ حُسم مرجع قطع الحركات CARD-003؛ حُسمت صيغة المطلوب والمسار CARD-004؛ تبقى تفاصيل التراكم وبقية حالات التقويم المحددة ضمن OPEN-006. هذه حالات تحقق مستقبلية، ولا تعني تنفيذ التطبيق أو اختبار قاعدة بيانات.

### 10.8 قبول إسناد المتابعة اليومية — CAL-005، حالات مخططة

**تصميم تنفيذ مقترح:** يوم متابعة الأهداف معلومة مشتقة مرتبطة بتقويم الموظف وفترة الهدف وإصدارهما؛ تاريخ المصدر محفوظ. لا يكتب الإسناد في DocumentDate أو تاريخ Ledger أو يوم الخرائط. تتحدث الأيام المتأثرة بنتيجة متسقة في الفترات المفتوحة، وتبقى نسخ الإقفال وفق PERIOD-001/002.

| الحالة | النتيجة المطلوبة |
| --- | --- |
| الجمعة مستثنى والخميس يوم عمل داخل الفترة | حركة الجمعة ضمن متابعة الخميس، مع ظهور تاريخ السند الأصلي عند فتحه |
| عدة عطل متتالية ولها يوم عمل سابق | جميع حركاتها مع أقرب يوم عمل سابق داخل الفترة، دون تكرارها في المجاميع |
| الفترة تبدأ بأيام مستثناة ولا سابق داخلها | الإسناد إلى أول يوم عمل تالٍ داخل الفترة، لا آخر يوم في الفترة السابقة |
| يوم مستثنى في نهاية الفترة وله يوم عمل سابق | الإسناد إلى السابق داخلها، دون ترحيل إلى الفترة التالية |
| الفترة كلها بلا أيام عمل | مجموعة «حركات أيام مستثناة» ضمن إجمالي الفترة بشروط CAL-004، دون هدف يومي أو تحقيق افتراضي |
| حركة في يوم عمل عادي | تبقى في يومها؛ لا تطبق قاعدة نقل حركات العطل عليها |
| مبيعات ومرتجعات وتحصيلات مؤهلة | نفس قاعدة الإسناد لكل نوع مع الحفاظ على مقاييسه؛ التحصيل لا يجمع مع المبيعات |
| تفاصيل الأصل والعرض اليومي مع إجمالي الفترة | كل حركة تحتسب مرة واحدة؛ العرض التفصيلي للأصل لا ينشئ أثرًا إضافيًا |
| كشف حساب/ذمم/FIFO وخريطة | لا تغير في تواريخها أو ترتيبها أو قواعدها بسبب إسناد أهداف يومي |
| تعديل تقويم/استثناء لفترة مفتوحة | تحديث الأيام والنتائج المتأثرة من المصدر نفسه دون نقل مالي أو تغيير نسخة عمولة مقفلة |

حُسم عقد اختيار الحركات حتى اليوم/الأمس في CARD-003 بتاريخ السند الأصلي قبل الإسناد؛ حُسمت صيغة المسار والمطلوب CARD-004؛ تبقى التفاصيل المحددة للتراكم والمقاييس OPEN-006/036. الافتراضي الميلادي حُسم لاحقًا في CAL-006، وأيام العمل والعطل في CAL-007؛ الفترة المخصصة لا تحسم بمجرد استعمال المثال. لم تنفذ اختبارات تطبيق أو حمل ضمن هذا التوثيق.

### 10.9 قبول الشهر الميلادي وتنسيق التواريخ — CAL-006/DATE-001، حالات مخططة

**متطلب العرض:** اليوم D/M/YYYY مثل `1/12/2026`، والشهر M/YYYY مثل `12/2026`، في جميع الواجهات والمخرجات. **تصميم تنفيذ مقترح:** تنسيق موحد للعرض لا يغير القيمة الأصلية. تحفظ صادرات Excel قيمة قابلة للفرز كتاريخ/فترة وتعرض بالتنسيق المطلوب؛ لا تعتمد العمليات المالية على نص العرض. تبقى قراءة عقد المصدر DD/MM/YYYY كما وثقت، ولا تفسر 1/12 على أنه شهر/يوم.

| الحالة | النتيجة المطلوبة |
| --- | --- |
| الفترة الافتراضية 12/2026 | من 1/12/2026 إلى 31/12/2026، والفترة متطابقة في الخطة والبطاقة وكشف العمولة |
| اختلاف طول الشهر | 2/2026 ينتهي في 28/2/2026، و2/2028 في 29/2/2028؛ لا يفترض طول ثابت لكل شهر |
| قيمة أول ديسمبر 2026 | تعرض `1/12/2026` في جميع الصفحات؛ لا تقلب إلى 12 يناير بسبب لغة الجهاز |
| اختيار/عرض شهر | يعرض `12/2026` مع السنة، وليس رقم شهر منفردًا أو تاريخ يوم مختلق |
| فرز أشهر 2/2026 و12/2026 | ترتيب زمني صحيح حسب السنة والشهر، لا ترتيب نصي |
| واجهة RTL وتقرير مطبوع | ترتيب اليوم/الشهر/السنة ثابت وواضح، والتنسيق متطابق مع PDF وExcel والمعاينة |
| تاريخ المصدر 01/12/2026 مقابل عرض 1/12/2026 | قيمة تاريخ واحدة وهوية سند واحدة، مع حفظ المصدر وعدم تكرار أثر إعادة الرفع |
| عرض تاريخ في كشف الحساب | التاريخ بالتنسيق المعتمد، والوقت يبقى ملغى وفق STMT-008 |
| تغيير شكل العرض | لا تغيير في DocumentDate أو السنة المالية أو Ledger/FIFO أو يوم الخرائط أو شروط اختيار السعر التاريخي |
| اقتراح فترة 26–25 | لا تفعّل أو تعرض كخيار معتمد قبل حسم OPEN-006؛ اعتماد الافتراضي وحده لا يعتمد المخصص |

هذه حالات مخططة؛ لم تنفذ واجهات أو ملفات تصدير أو اختبارات تطبيق. السنة/الشهر وتاريخ اليوم مدخلات مختلفة، وتخزينها الداخلي وعرضها لا يختلطان.

### 10.10 قبول أيام العمل والعطل العامة — CAL-007، حالات مخططة

يحسب الأساس من التقويم العام بعد العطل الأسبوعية والعامة وقبل الاستثناءات الشخصية. بقاء الهدف الأصلي لا يعني بقاء ناتج التناسب إذا تغير الأساس. الأرقام التالية أمثلة لموظف مؤهل طوال الفترة ومكون هدف يشمله التناسب، ولا تحسم بذاتها تقريب الأهداف العددية؛ حدود الأهلية حُسمت EMP-003 وأثر الشهر الجزئي حُسم CAL-008.

| الحالة | النتيجة المطلوبة |
| --- | --- |
| التقويم الافتراضي | السبت إلى الخميس أيام عمل والجمعة عطلة، مع إمكانية تعديل أيام الأسبوع |
| إضافة عطلة عامة | يوم أو فترة باسم وسبب، وتظهر ضمن التقويم العام؛ تستبعد أيام العمل التي تغطيها مرة واحدة |
| 26 يومًا وهدف 10,000، عطلة عامة في يوم عمل، دون استثناءات شخصية | الأساس 25 والهدف الأصلي والمعدل 10,000 ومتوسط اليوم 400 |
| عطلة عامة يوم الجمعة المستثنى أصلًا أو عطل عامة متداخلة | لا خصم إضافي لليوم المستثنى ولا مضاعفة عدد الأيام |
| بعد العطلة صار الأساس 25، وثلاثة أيام شخصية متناسبة مختلفة ما زالت مؤهلة | 22 يومًا للموظف، والأصل 10,000، والمعدل 8,800؛ الاشتقاق من الأصل والأساس الحالي |
| أحد أيام الاستثناء الشخصي صار عطلة عامة | لا يحسب مرة ثانية ضمن الأيام الشخصية المؤهلة، سواء كان ثابتًا أو متناسبًا؛ لا حذف لنمط الاستثناء ولا تخفيض مكرر |
| العطلة العامة تضيف أو تعدل في فترة مفتوحة | الأهداف والبطاقات والإسناد اليومي تستخدم التقويم نفسه، مع سجل التغيير وإعادة اشتقاق النطاق المتأثر |

### 10.12 قبول هدف الشهر الجزئي والاستثناءات — CAL-008، حالات مخططة

مرجع الحساب هو T الأصلي، وD أيام الشهر بعد العطل العامة، وE أيام العمل داخل فترات الأهلية قبل الاستثناءات، وP الأيام الشخصية المتناسبة، وX جميع الأيام الشخصية المستثناة المؤهلة دون تكرار. مع D وE موجبتين: B = T × E ÷ D للمتناسب أو T للثابت؛ النهائي = B × (E − P) ÷ E، والأيام المتبقية = E − X.

| D=0 أو E=0، أو انعدام الأيام المتبقية | لا قسمة على صفر أو تحقيق تلقائي؛ تفاصيل النتيجة والاستحقاق تستكمل OPEN-006/036 |

| تعديل القالب ثم استخدامه لخطة جديدة | تنقل الإعدادات المعدلة عند الاستخدام الجديد |
| تعديل القالب وله خطط سابقة | لا تتغير الخطط السابقة تلقائيًا |
| طلب تحديث خطة سابقة من القالب | إجراء صريح مع معاينة التغييرات قبل التطبيق؛ المعاينة وحدها لا تعدل الخطة |
| خطة لفترة مقفلة | لا يتجاوز تحديث القالب حماية PERIOD-001/002 |

حالات تحقق مخططة، لا اختبارات تطبيق منفذة. إعادة اشتقاق الهدف والصلاحيات والسجل تتبع القواعد المعتمدة.

## 11. ما يُقاس قبل إعلان الجاهزية

اعتماد عقود وقواعد → اختبارات حالات حساسة → تجربة مسار كامل بملفات ممثلة → مطابقة مبالغ وcounts ومخرجات → اختبار صلاحيات ونشر وطباعة → حمل وحالات انقطاع/استئناف → تسليم بنتائج موثقة وحدود تشغيل معلنة.
